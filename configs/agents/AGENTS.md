# 全局开发指导（平台共性）

本文件提供在内部开发环境中通用的指导原则，适用于所有项目。

## 交互原则（不迎合）

- **先审题**：回答前先检查提问里有没有错误前提、逻辑跳跃或信息缺失；发现错误前提先纠正，不顺着往下答。
- **独立判断**：不迎合用户观点——即使用户的想法是错的，也直接指出，并给出依据、风险与替代解释。
- **区分事实 / 推测 / 观点**：明确标注哪些是已核实的事实、哪些是推测、哪些是主观观点。
- **关键信息核实**：涉及数字、人物、结论时尽量核实来源；不确定就明说，不编造。
- **主动提醒盲区**：指出用户可能忽略的变量、隐性成本与偏差。

## 网络访问

访问境外开发资源（`github.com`、npm registry、`docker hub / ghcr.io`、`huggingface.co`、`pypi.org` 等）失败时，优先确认代理环境变量是否生效，而不是放弃操作：

- 代理**默认关闭**，按需手动开启：交互 shell 的 rc 已 source `~/.config/shell/proxy.env`（提供 `proxy_on` / `proxy_off` 开关函数；约定见 `tools/proxy.md`），直接 `proxy_on`。确认当前会话变量存在（`env | grep -i proxy`）；非登录 shell、容器、`sudo` 等场景没有 `proxy_on` 函数时，先 `source ~/.config/shell/proxy.env` 再开启。
- 只认大写变量的工具用 `HTTP_PROXY` / `HTTPS_PROXY`；`git` 单独配时 `git config --global http.proxy`，取值与 shell 环境一致。
- **不在此文件写死代理地址**——各环境入口地址可能不同，一律以环境变量为准。

## 凭据约定

- 密钥 / token 统一放 `~/.config/shell/secrets.env`（权限 600，不入版本管理），由登录 shell 幂等 source（约定见 `tools/shell.md`）。
- 需要 key 的工具（coding agent / MCP 等）一律读环境变量；**绝不把凭据写进仓库、配置文件明文或日志**。

## 代码注释规范

注释面向未来的维护者，记录**持久的技术理由与非显而易见的约束**，而不是开发过程的流水账。

- **写"为什么"，不写"怎么走到这一步"**：解释设计决策与约束（为何锁定某个版本、并发模型、为何复用某段代码），而不是调试历史（"我们试过 A，又试过 B""之前是……"）这类过程叙述。
- **构建/配置产物不要耦合临时环境**：Dockerfile、docker-compose、配置文件里的注释，不应把决策理由绑定到某次部署的具体环境事实——例如"宿主驱动只到 CUDA 12.9""在 T4 上……"。这类信息会随部署变化而过时甚至误导。改写为通用的持久理由（如"用 CUDA-12 构建，兼容更广的驱动；新版 torch 默认 CUDA 13"）。
- **不要把开发对话里的偏好写进产物**："按你的要求避免 apt""为了图快"等是过程性指令，不是技术理由，不应残留在代码注释里。
- **区分产物注释与用户文档**：README 等面向用户的文档里，用具体硬件（如 T4、16 GB）作举例说明是合理的（给读者指引）；但同样的硬件信息作为硬编码进 Dockerfile/compose 的决策依据就不合适。

一句话：代码/配置注释 = 给维护者的持久技术理由；过程、偏好、某次部署的临时事实，都不该留下。
